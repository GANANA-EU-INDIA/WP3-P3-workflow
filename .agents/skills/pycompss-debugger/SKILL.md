Conventions: Makefile → wrapper/submit_workflow.sh → wrapper/env_config_<cluster>.sh → workflow/md.py → workflow/md-provenance.yaml. Primary debug target: `.COMPSs` output directory from Makefile.

## Process
1. Locate submission path and workflow files.
2. If `--debug`/`-d`, `--worker_working_dir=$(pwd)` (or `--worker_working_directory=$(pwd)` — flag name varies by version, check `runcompss -h`), and `--keep_workingdir` aren't already in the submission command, ask the user to add them and re-run before going further. See "Debug flags" below for why.
3. Inspect `.COMPSs` output, Slurm logs, workflow stderr/stdout. Start with the tail of `runtime.log` — transfer and job-submission failures surface there first — then move to `jobs/JOB<N>_NEW.{out,err}` for task-level failures. A matching `*_RESUBMITTED.*` file means the job failed once already; its original log often has the more informative error.
4. `web_search` docs at `compss-doc.readthedocs.io` for error patterns not covered below.
5. Cross-reference logs against docs and the "COMPSs internals" / "Known failure patterns" sections below before diagnosing (use internally).
6. If checkpointing is involved, read "Checkpointing pitfall" below before trusting that a task ID mismatch means "not executed" or "already executed."
7. Propose fix aligned with repo conventions.

## Debug flags
Ask the user to add these if missing — most failures aren't diagnosable without them:
- `--debug` / `-d`: unlocks full per-task output in `jobs/`, plus `runtime.log`, `pycompss.log`/`.err`, `resources.log`, and per-worker `worker_<NODE>.{out,err}` / `binding_worker_<NODE>.{out,err}`.
- `--worker_working_dir=$(pwd)`: makes workers use the current directory, so a `tmp_XXXXXX` folder shows up there instead of only existing on the remote worker.
- `--keep_workingdir`: stops that `tmp_XXXXXX` folder from being deleted once the job ends, so it's still there to inspect.
- `--gen_coredump` (only if the above isn't enough): generates a core dump on segfault.

## COMPSs internals to keep in mind
- The runtime renames/re-IDs data and tasks internally — names in the source rarely match what appears in logs. Match by task order and structure, not by name.
- Workers execute inside a sandboxed working directory, not the original one. Hardcoded or relative paths inside a task can silently resolve to the wrong place — this is also why files not declared as task parameters won't show up where expected, and why launch-directory-relative cleanup logic can misbehave.

## Known failure patterns (from COMPSs troubleshooting docs)
- Tasks stuck **Blocked**: no resource matches the task's constraints, or resources didn't load — check `resources.log` against `project.xml`/`resources.xml`.
- **All** jobs fail immediately: usually missing passwordless SSH to a resource — check the `User` tag per resource in `project.xml`, test `ssh user@resource` manually.
- Worker won't start (`InitNodeException`, `UnstartedNodeException`, connection refused): check `JAVA_HOME` and working-dir permissions on that worker; "no exception, still fails" usually means a firewall blocking the adaptor ports (43000–44000 by default).
- Empty `workers/` folder: the runtime couldn't retrieve worker logs at all — connect to the worker directly, or point the worker working-dir flag at a shared filesystem location.
- Tracing merge fails with "too many open files": use Extrae's parallel MPI merger (if COMPSs was built with MPI support) or raise `ulimit -n`.
- Master and workers pointed at differently-performing mount points (e.g. scratch vs. project-style filesystems) is a quiet, common performance killer — worth ruling out before assuming a code-level bottleneck. Relevant on Leonardo/Dardel-style multi-filesystem setups.
- Exceptions raised inside a task never propagate a traceback to the master — the master only reports the task as failed. The real exception is always in that task's own job log, not the main stdout/stderr.
- Python global-state modules (e.g. `logging`) and global variables aren't reliable across master/worker, since each runs in a separate interpreter. "Behaves differently when run as a worker" is a hint to check for this before assuming a runtime bug.

## Checkpointing pitfall
When checkpointing is in play, surface this before diagnosing a "task wrongly seen as already-done" or "wrong result reused" issue:

> The problem is how the COMPSs runtime manages the renaming of internal values throughout two executions of the same workflow. Rather than identifying each task by its operation and input data, the checkpointing mechanism relies on an identifier of the task that is generated by increasing a counter every time a task is detected. As the original execution progresses, the checkpoint writes to a checkpointing log file all the tasks that have finished and whose results have been saved for a later execution.
>
> When the code changes, the task IDs on the two executions no longer match — this especially shows up in iterative code. For a loop with 5 tasks, the first task of each iteration would normally be numbered 1, 6, 11, 16, .... Add two more tasks per iteration and the gap grows every iteration: 1, 8, 15, 22, ....
>
> This causes three problems:
> 1. The runtime believes tasks it hasn't executed — but that belong to the original workflow — are unexecuted, simply because their ID is now larger than what's in the checkpoint log.
> 2. The runtime believes new tasks were already executed, because their ID happens to already be in the log.
> 3. The runtime registers the original task's result as if it belonged to the new task.
>
> Splitting the loop in two keeps the IDs stable for every task in the original workflow; the new part generates new tasks whose IDs are guaranteed not to already be in the checkpoint log.
>
> Checkpointing was designed for re-running the same workflow after a failure, not for resuming a modified workflow. Using it that way is a known gap — discussed with Javi as a possible future direction, not something COMPSs supports today.
